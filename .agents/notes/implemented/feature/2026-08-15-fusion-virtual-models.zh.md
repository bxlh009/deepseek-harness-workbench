# Agent Note：融合虚拟模型

状态：已实现

[English](2026-08-15-fusion-virtual-models.md) | 中文

## 问题

模型设置页可以配置提供方路由，但不能把可复用的多模型流程暴露成一个模型。隐藏工具依赖模型主动调用，也不会让组合后的路由出现在对话模型选择器中。

## 决策

增加由设置驱动的 `@deepseek-ai/dsh-llm-fusion` 适配器。每个配置在固定的 `fusion` 提供方下发布一个模型，并行运行二至四个互不重复且禁用工具的候选路由，再把有长度上限的文本草案交给指定汇总路由。汇总模型接收原始工具，并通过正常 Agent 循环流式输出答案。

模型设置页读取实时模型目录，提供一等的“融合模型”编辑器，并把配置写入 `llm-fusion` 命名空间。只有至少存在一个有效配置时，适配器才注册提供方，因此现有模型目录和选择器无需增加融合专用分支。

每个配置可以选择一个支持图片的视觉代理。启用后，融合模型声明支持图片输入；每组不同附件只发送给视觉代理一次，随后把所有图片块替换为文字标记，并把有长度上限的视觉报告作为可能出错的证据交给候选和汇总路由。未配置视觉代理的融合模型仍然只支持文字。这样，纯文本提供方不会收到图片字节，用户仍可通过普通对话框直接粘贴或上传图片。

自定义提供方卡片为 Groq 和 Gemini 的 OpenAI 兼容端点提供云端视觉快捷配置。每个快捷配置都声明一个支持图片的模型并要求填写 API 密钥；密钥仍通过现有只写凭据服务保存，不进入 settings。免费额度和数据处理规则由提供方控制。在任何融合配置能够使用视觉路由之前，界面和适配器校验都会要求持久化确认：上传的图片字节会离开本地应用并发送给该提供方。

适配器还通过 `llm/stream` 瀑布流提供可选的全局视觉代理。它只检查包含图片的请求；声明原生图片输入能力的模型会直接跳过，否则先执行同一套带缓存的“图片转报告”处理，再重新调用原提供方和模型。内部识图调用携带仅在当前进程有效的绕过标记，因此不会递归触发全局代理。设置页在启用前同样要求持久化确认图片外发。

同一页面还提供用于收集证据的盲测竞技场。宿主的 `llm.arena` RPC 用同一条题目并发运行某个方案的候选路由与融合路由，不带工具或 Session 历史。浏览器在用户选出胜者前隐藏路由身份，随后揭示耗时与 token 用量，并在内存中累计胜场。

## 考虑过的替代方案

**模型可见的委员会工具。** 放弃，因为它不是可选择的模型，而且语言模型可能选择不调用。

**修改核心 Agent 循环。** 放弃，因为组合应位于提供方无关的 LLM 适配器边界之后，不应改变普通单模型会话。

**递归融合。** 放弃，以限制请求数量并避免循环。

**只安装视觉 MCP 服务器。** 不作为对话链路，因为 MCP 工具无法在纯文本模型收到回合之前截获已粘贴的图片。视觉代理在可选择的适配器路由内部采用与 [`vision-mcp`](https://github.com/Pelican0126/vision-mcp) 相同的“图片转文字”模式。

## 后果

- 每次融合推理会产生“候选数 + 1”次模型调用，延迟和成本可能高于单模型。
- 候选模型禁用工具；只有汇总模型可以发出可执行工具调用。
- 每轮竞技场会调用每个候选一次，再执行一次完整融合推理；评分刻意由用户完成，不让被比较的某个模型充当评委。
- 使用新附件组合时，启用视觉代理的推理会额外调用一次视觉模型；同一 Agent 回合的后续步骤复用内存中的报告。
- 设置界面只把明确声明支持图片的模型列为视觉代理选项，并说明上传图片会发送给该路由。
- Groq 和 Gemini 快捷配置把云端视觉设置缩减为填写密钥并复核声明的路由；模型会动态变化的聚合平台继续通过通用自定义提供方表单接入，避免硬编码一个很快过时的免费模型。
- 视觉配置只有在 `shareImagesWithVisionProvider` 明确为 `true` 时才能保存或加载；这只是披露与同意，不代表对提供方数据保留政策作出保证。
- 全局代理只处理包含图片且所选模型未声明图片输入能力的调用；原生视觉路由保持不变。
- 配置会拒绝重复 ID、重复路由、递归融合路由，以及少于二个或多于四个候选。

## 测试

适配器测试覆盖目录注册、候选隔离、单次视觉预处理、图片移除、汇总上下文、工具转发、同意校验和无效定义。宿主与组件测试覆盖云端提供方快捷配置、凭据门控、同意门控、无工具竞技场分发、匿名展示、揭晓、指标与投票。
